# Pre-Review Summary as a separate Claude pipeline, not a stage of Review

We want a per-PR-card "what / why / risk" TL;DR generated by Claude. The natural temptation is to fold this into the existing Review pipeline (worktree + full tools + main concurrency pool). We chose instead to build it as a parallel, lightweight pipeline.

The Pre-Review Summary uses `claude -p` with `Bash(gh:*)` only — no worktree, no clone, no `git`/`Read`/`Grep`/`Glob`. It runs on its own concurrency pool (separate from the Review cap of 3) and is keyed and cached by `(repo, prNumber, headSha)` independently of `Review`. It is manually triggered per card via a "Summarize" button; the cache is consulted first, the Claude call happens only on cache miss.

Folding into Review was rejected because the use case is decision support for *whether* to review — making it depend on the worktree/clone path means summary latency is gated by the slowest-path infrastructure of the Review system, and cancelling/queueing semantics get tangled. Auto-running on PR list refresh was rejected because it violates the manual-cost-control principle in the PRD ("the app never spends my Claude credits without me asking"). Free-riding on the Review run (computing summary as part of Review) was rejected because it makes the summary useless for its actual purpose: deciding whether to review.

## Consequences

Two Claude pipelines coexist with similar shape but distinct concurrency, caching, tool allowance, and trigger surfaces. Future ADRs that change Claude integration (model selection, output schema validation, retry strategy) need to consider both. The structural duplication is the price of the separation we want.
